# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Ruby version manager

This project pins its Ruby version via `mise` (see `mise.toml`), not system Ruby. The shell is not mise-activated in this environment, so any bare `bin/*` script (`bin/rails`, `bin/rubocop`, `bin/ci`, ...) resolves to the system Ruby (2.6) and fails with a Bundler platform error on this Gemfile. Prefix every `bin/*` invocation with `mise exec --`, e.g.:

```bash
mise exec -- bin/rails db:migrate
mise exec -- bin/rails generate migration AddFooToBar
mise exec -- bin/rails test
```

## Commands

- Run the dev server (web + Tailwind watcher + Solid Queue jobs, via Foreman): `bin/dev`

## Architecture

This is a feed reader: `Feed has_many :items`. Feeds are polled and parsed with Ruby's stdlib `rss` gem, which supports both RSS and Atom — parsing is normalized behind a small adapter layer so the rest of the app never branches on format.

- `ParsedFeed` (`app/services/parsed_feed.rb`) — wraps `RSS::Parser.parse`'s result (either an `RSS::Rss` or `RSS::Atom::Feed` instance) and exposes format-agnostic `#title`/`#description`/`#link`/`#entries`. Parses with `do_validate: false` (`RSS::Parser.parse(source, false)`) — the gem's default (`true`) enforces strict RSS/Atom schema compliance, including required tags that are routinely absent from real, working feeds. Confirmed live: `https://37signals.com/feed/jobs.xml` — a real feed a user tried to add — raised `RSS::MissingTagError: tag <author> is missing in tag <feed>` under the default and parses cleanly with it off. `ParsedFeed`/`ParsedFeedEntry` already navigate every field with `&.`, so a field that's genuinely absent under lenient parsing just comes back `nil` rather than raising; `Feed#validates_presence_of :link` is the actual backstop against an unusably broken feed, not this. `ParsedFeedEntry` (`app/services/parsed_feed_entry.rb`) does the same per-entry (`#title`/`#summary`/`#link`/`#guid`/`#published_at`), preferring Atom's `summary` over `content` and falling back to `updated` when `published` is absent (it's optional in Atom). `AtomLink` (`app/services/atom_link.rb`) picks the `rel="alternate"` link out of Atom's multi-`<link>` elements (RSS only ever has one link, no resolution needed). This is the layer to extend for any new source format or field.
- `InitializeFeed` (`app/services/initialize_feed.rb`) — parses a feed URL via `ParsedFeed.parse`, builds an unsaved `Feed` with nested `items` (via `accepts_nested_attributes_for`). Rescues `RSS::Error` (malformed XML, or a real structural problem even under `ParsedFeed`'s lenient `do_validate: false` — e.g. unparseable XML entirely, not merely a missing optional-in-practice tag) and returns an unsaved `Feed` with a validation error on `:link` instead of raising, so the controller can re-render the form. **`FeedsController#create` must not call `feed.save` when `feed.errors` is already populated this way.** `save` calls `valid?` internally, which clears `errors` before re-running validations — so the specific message `InitializeFeed` attached (e.g. "Couldn't find a feed at that address.") got silently replaced by the generic `Link can't be blank` from `validates_presence_of :link` (the rescue path's `Feed.new(user: @user)` never sets `link:`). This was a real, live bug — the informative message was dead code from the day it was written, masked because nothing tested the dialog's actual error text. Fixed by short-circuiting: `if feed.errors.empty? && feed.save`.
- `InitializeItems` (`app/services/initialize_items.rb`) — maps `ParsedFeedEntry` objects into unsaved `Item` records.
- `UpdateFeedsJob` (`app/jobs/update_feeds_job.rb`) — scheduled job (see `config/recurring.yml`, runs every minute in development via Solid Queue's recurring scheduler) that re-polls each `Feed.feed_url` and appends newly-published items. It fetches with `FeedFetcher` (`app/services/feed_fetcher.rb`, plain `Net::HTTP`), **not** by handing the URL to `RSS::Parser.parse` — open-uri hid the status, size and validators and raised on anything non-2xx. `FeedFetcher` sends a conditional GET from the feed's stored `etag`/`last_modified` (304 → nothing parsed), follows up to 5 redirects (reported as `redirects`, feed URL left unchanged), caps bodies at 10 MB, and *returns* non-2xx responses rather than raising. Bodies are parsed with `ParsedFeed.parse_xml`, never `ParsedFeed.parse`: the rss gem's `normalize_rss` treats any string without a `<` as a URL to fetch or a **local file path to read**, so a fetched body must never reach it unguarded. Dedup is identity-based (`guid.presence || link`, compared against existing items' `guid`/`link`), not date-based — this is required for Atom, where `published` is optional, and is more robust for RSS too. A per-feed `rescue StandardError` keeps one broken/unreachable feed from aborting the loop for every feed after it (transport errors — `Errno::ECONNREFUSED`, `SocketError`, `Net::OpenTimeout` — are not `RSS::Error`; this was a real bug once). Every poll, success or failure, goes through `Feed#record_fetch!`, which writes a `FetchEvent` (the FetchLog rows; `status` is the HTTP code or, with no usable response, a word from `UpdateFeedsJob::FAILURE_WORDS` — `TIMEOUT`/`DNS`/`CONN`/`TLS`/`PARSE`/`REDIR`/`SIZE`/`URL`/`ERR`), updates `last_fetched_at`/`last_fetch_status`/`last_fetch_detail`, tracks the failure streak (`last_fetch_error_at` + `fetch_failures_count`, both reset on the next success) and broadcasts the feed-tree row. `FetchEvent.tone` maps a status to its RDR-01 StatusCode tone (ok/warn/fail); events older than `FetchEvent::RETENTION` (1 day) are pruned at the end of each run. This is a different concern from `InitializeFeed`'s `rescue RSS::Error` above — that one validates a feed URL *at creation time* and still calls `ParsedFeed.parse` with the raw user input (see Known deferred fixes).
- Background jobs run on Solid Queue with a separate `queue` database (`config/database.yml`); Mission Control Jobs is mounted at `/jobs` (`config/routes.rb`) for inspecting job state.
- New items broadcast live to the feed show page over Action Cable: `Item#after_create_commit` calls `broadcast_prepend_to feed, target: "items", partial: "items/list_item"`, and `feeds/show.html.erb` subscribes via `turbo_stream_from @feed`, prepending into `<div id="items">`. This fires for items created anywhere (nested-attributes save on feed creation, or `UpdateFeedsJob`), not just the job.
- Unread tracking is per-item (`items.read`, boolean, default `false`), not per-feed — opening a feed does **not** mark its items read; only opening an individual item does, via `ItemsController#show` calling `Item#mark_read!`. `Feed#unread_count` (`items.unread.count`) drives the sidebar pill in `feeds/_feed.html.erb`; `items/_list_item.html.erb` renders a small dot per unread item. Both the pill and the per-item dot update live: `Item#broadcast_creation` (on create) and `Item#mark_read!` (on read) both broadcast a `feeds/_feed` replace (via `Feed#broadcast_row`/`#broadcast_row_later`) to the owning user's own `[user, :feeds]` stream, which `feeds/index.html.erb` subscribes to once (`turbo_stream_from Current.user, :feeds`, placed outside any turbo-frame so it survives frame navigations — same reasoning as the `@feed` stream fix below). `mark_read!` uses the `_later` broadcast variants since it runs inside a controller action (see Verified library behavior below for why that matters). It used to be one global `:feeds` stream shared by every account — which pushed every user's rendered feed rows (titles included) to every connected client. Never broadcast feed rows to an unscoped stream again.
- Feed creation is Turbo-Stream driven: `FeedsController#create` appends a rendered `feeds/feed` partial to the `feeds` list on success, or re-renders `new` with errors for a Turbo Stream response.
- `ItemsController#show` is genuinely wired into the UI — the item title link (`items/_list_item.html.erb`) targets it via `turbo_frame: "current_item"`, and it's also where `mark_read!` gets triggered. Only `new`/`edit`/`create`/`update`/`destroy` are unused `rails generate scaffold` leftovers — don't treat *those* as a real feature surface to build around.
- Feed-supplied HTML (`item.summary`) is rendered via `ItemsHelper#sanitized_summary`, not a bare `sanitize` call — Rails' default sanitizer allow-list has no `table`/`tr`/`td`/`th` at all, so it silently drops any table a feed embeds. `ItemsHelper::SUMMARY_ALLOWED_TAGS` is an explicit list matching what the reader's `.r-body` rules (`app/assets/tailwind/application.css`) actually style, not "the default list plus tables" — that would also let through tags (`dl`/`kbd`/`samp`/`mark`/...) with no treatment there.
- The UI follows the **RDR-01** design system (https://claude.ai/artifact/2phj7G2SbeN6DJEKGaD1Nd — its `project/README.md` is the brand book, `project/tokens.json` the tokens). Tokens live in `app/assets/tailwind/application.css`'s `@theme` (Paper values) plus two Carbon override blocks on `<body>`; its components (`r-*` classes) are ported from the system's `components/bundle.css` into the same file, with `var(--paper)` renamed to Tailwind's `var(--color-paper)`. App-only additions (`rdr-*` shell/panes, dialog, publisher-HTML rules under `.r-body`) come after the "App-specific" marker. The StatusBar (`layouts/_status_bar.html.erb`) computes its FEEDS/UNREAD/LAST FETCH/ERR cells client-side (`status_bar_controller.js`) from the feed tree rows' `data-unread`/`data-health`/`data-fetched-at`, which the per-user feeds stream already keeps live — don't add a separate server broadcast for it. Under 1100px the reader replaces the item table, driven by `data-reading` on `.rdr-panes` (`selection_controller.js`). Keyboard shortcuts all live in `selection_controller.js` (`key` for page-wide single keys, `treeKey` for the feed tree's roving-tabindex arrow navigation); RDR-01 requires each shortcut to be printed on its control (`<span class="r-key">`), and `feeds/_keys.html.erb` (the `?` dialog) lists them all — keep the three in step. J/K deliberately move a cursor rather than open the item, so skimming never triggers `Item#mark_read!`.
- Feed tree folders: `Folder` (`belongs_to :user`, `has_many :feeds, dependent: :nullify`, unique `name` per user, persisted `collapsed`), one level deep, `feeds.folder_id` nullable (= top level). Feeds are filed **by name** via `Feed#folder_name=` (blank → top level, unknown name → folder created for the feed's owner) from both the Add feed dialog and the context menu's Move dialog (`FeedsController#update`). The tree (`feeds/_tree.html.erb`) is a *flat* list — folder row, then its feeds as `r-child` rows carrying `data-parent-folder` (and `hidden` while collapsed) — so structural changes (add/move/delete feed, rename/delete folder) re-render the whole tree through `FeedTreeStreams#tree_streams` rather than splicing rows; count/health changes still replace single rows, and `Feed#broadcast_row` also re-renders the feed's folder row since it aggregates unread and worst health. Folder rows have `data-folder-id` but no `data-feed-id`, so the StatusBar never double-counts them. Collapse is toggled client-side in `selection_controller.js` (click, Enter, ←/→) and saved with a background JSON `PATCH /folders/:id`.
- Item triage: `items.marked` (RDR-01's one-keypress "marked" state, independent of read) is toggled by `Items::MarksController` (`POST`/`DELETE /items/:item_id/mark`), which answers with Turbo Streams replacing the list row and the reader's MARK button — the M key sends the same request from JS and renders the response with `window.Turbo.renderStreamMessage`. "Mark all read" is `Feeds::ReadingsController#create` (`POST /feeds/:feed_id/reading` → `Feed#mark_all_read!`, a single `update_all`, then a later broadcast of the tree row). The Marked view (`MarkedItemsController#index`, `GET /marked`, opened from the fixed MARKED row that `feeds/_tree.html.erb` always renders first) lists every marked item across feeds in the `current_feed` frame; its count uses the `mark` token, never `signal`. Item rows (`items/_list_item.html.erb`) always render a Feed cell so one streamed row replace fits both tables — a single feed's table hides it with `.rdr-single-feed .r-feed { display: none }`. Each item list's `#items` names its tree row in `data-tree-row` (`feed_12` or `marked_view`), which `selection_controller.js#feedNavigated` selects. Unmarking in the Marked view leaves the row in place (unhighlighted) until reload, so M again re-marks it. The unread-only filter is a per-user preference (`users.unread_only`) saved through `PreferencesController`, which redirects to `url_from(params[:return_to])` because the toolbar sits inside the `current_feed` frame (the Referer is the page, not the frame). A row read while the filter is on stays in the list until the next load, on purpose, so the cursor never jumps. Letter shortcuts are matched case-insensitively with Shift as an explicit modifier (`selection_controller.js#combo`), never by `event.key`'s case — Caps Lock flips the case without Shift.
- Accounts are per-user, real multi-tenancy, not a single shared login: `Feed belongs_to :user`, `User has_many :feeds`/`has_many :items, through: :feeds`. `FeedsController`/`ItemsController` scope every lookup through `Current.user` (`Current.user.feeds`, `Current.user.items`) rather than `Feed.all`/`Item.find` — never reintroduce an unscoped `Feed`/`Item` lookup in a controller, it'd leak across accounts. `InitializeFeed.new(link:, user:)` takes the owner explicitly and sets it on both the success and `RSS::Error` rescue paths. `UpdateFeedsJob` is the one legitimate exception — it deliberately iterates `Feed.all` since it's a background job with no "current user," not a request.

### Nomenclature: RSS vs. Atom

`Item#published_at` (not `pub_date`) and `Item#summary` (not `description`) are named to stay parser-agnostic: they map to either RSS (`pubDate`/`description`) or Atom (`published`/`summary`|`content`) source fields via the `ParsedFeed`/`ParsedFeedEntry` adapter above. `Item#guid` (nullable, unique per `feed_id`) holds RSS's optional `<guid>` or Atom's required `<id>`, and is the dedup key `UpdateFeedsJob` uses.

## Database

SQLite, with separate `primary`/`queue`/`cache`/`cable` databases per `config/database.yml` (Solid Cache/Queue/Cable, each with their own `migrations_paths`). Migrations for the primary app schema live in `db/migrate/` and are generated with `mise exec -- bin/rails generate migration ...`.

## Notes

- Action Cable uses `solid_cable` (DB-backed) in **both** development and production (`config/cable.yml`), not the Rails-default `async` adapter. `async` only pub-subs within a single process, and `bin/dev` runs the web server and the Solid Queue worker/scheduler as separate OS processes — a broadcast triggered from a job (e.g. `UpdateFeedsJob`) would never reach a browser connected to the web process under `async`. If Action Cable broadcasts silently don't arrive in development, check `config/cable.yml` hasn't reverted to `async` before debugging anything else. Action Cable config is only read at boot, so changing it requires restarting `bin/dev`, not just waiting for code reloading.
- **Migrations run against a separately-started `bin/dev` require a server restart, not just `db:migrate`.** `config.enable_reloading = true` reloads *code* changes, but each running server process caches its own copy of ActiveRecord's column/attribute-method introspection per model class — running a migration in a separate `mise exec -- bin/rails db:migrate` process doesn't invalidate that cache in the already-running server. Symptom: `NoMethodError: undefined method 'foo?'`/`'foo='` for a column that very much exists in `schema.rb` and works fine from a one-off `bin/rails runner`. Fix is always the same: restart `bin/dev`.
- `config/initializers/field_with_errors.rb` disables Rails' default error-wrapping `<div class="field_with_errors">` around invalid form fields (it just returns the tag unwrapped), since that wrapper breaks Tailwind styling. Keep this in mind when debugging why invalid-field styling isn't showing up automatically — error state has to be styled explicitly in the view/`error_class:` rather than relying on the wrapper.
- Test depth for this prototype: model/controller/job tests only. Don't add Capybara system tests unless asked.
- The "⚡ Tip" link in the layout (`app/views/layouts/application.html.erb`) is a static Lightning Address QR code (`app/assets/images/lightning_tip_qr.svg`, encodes `lightning:peartree@getalby.com`) opened via a native `<dialog>` — no backend integration, no gem dependency, no route. Lightning Addresses (LNURL-pay) let a wallet pay an arbitrary, repeatable amount from a fixed address alone, so there's nothing to run server-side. The SVG was generated once with the `rqrcode` gem (installed to user gem space via `gem install --user-install`, deliberately **not** added to the Gemfile — it was a one-time asset-generation tool, not a runtime dependency) and checked in as a static asset. If the tip address ever changes, regenerate the SVG the same way and replace the file; nothing else references it.

## Known deferred fixes

- **`InitializeFeed` still passes raw user input to `RSS::Parser.parse`.** The rss gem's `normalize_rss` reads any input without a `<` as a URL (via open-uri) or, failing that, as a **local file path** (`File.readable?` → `File.read`). So typing a server-side path into Add Feed makes the app read that file; an XML file there would be parsed and saved as a feed. Fix: fetch with `FeedFetcher` (which rejects non-http(s) URLs) and parse with `ParsedFeed.parse_xml`, as `UpdateFeedsJob` already does. The catch: `FeedsControllerTest`'s Atom test currently posts inline XML *as the link*, relying on exactly this quirk, and needs rewriting to stub `FeedFetcher.fetch`.
- **`feeds.user_id` is nullable and needs finalizing.** Added via `AddUserToFeeds` as nullable on purpose (existing feeds predated accounts, had no owner to backfill to at migration time — this is the standard safe pattern for adding a required association to a table with existing rows: add nullable, backfill, then tighten). Once the first real user account exists and any pre-existing feeds are reassigned to it (`Feed.where(user_id: nil).update_all(user_id: ...)`), add and run a follow-up migration (`change_column_null :feeds, :user_id, false`) to close the gap. Until then, `Feed belongs_to :user`'s presence validation blocks *saving* an ownerless feed but does nothing to rows already null in the DB.
- **`ItemsController#show` performs a side effect (`Item#mark_read!`) on a `GET` request — this is a real correctness bug, currently only masked, not fixed.** Turbo 8 prefetches links on hover with a real `GET` fetch of the destination, which means merely hovering an item's title (`items/_list_item.html.erb`) marks it read without the user ever opening it. Current mitigation: `data-turbo-prefetch="false"` on that link, disabling the prefetch. This treats the symptom, not the cause — `GET` should be safe/idempotent per HTTP semantics, and anything else that can trigger a GET without real navigation intent (browser back/forward-cache revalidation, opening in a new tab without reading, future browser speculative-loading features like Speculation Rules, link-preview bots if this app is ever exposed beyond localhost) could reintroduce the same bug elsewhere. Correct fix, deferred for now: split "view the item" (stays a side-effect-free `GET`) from "mark read" (a real `POST`/`PATCH` mutation), triggered by a small Stimulus controller's `connect()` callback on the item detail partial — `connect()` only fires when Turbo actually inserts that content into the live DOM (real navigation), not when it merely warms the prefetch cache.

## Verified library behavior

Facts below were confirmed against the actual installed gem source (not recalled from general knowledge), because exact behavior can shift across versions and this app pins specific ones. Re-verify anything here if the pinned version in `Gemfile.lock` changes. Fast lookup for anything *not* covered below: `mise exec -- bundle show <gem_name>` prints the gem's install path directly (no Rails boot needed) — grep from there rather than guessing at API shape.

**turbo-rails 2.0.23** (`Turbo::Broadcastable`, `app/models/concerns/turbo/broadcastable.rb` and `app/channels/turbo/streams/broadcasts.rb`):
- `broadcast_replace_to`/`broadcast_update_to`/etc. default `target: self` unless you pass `target:` explicitly. Passing an ActiveRecord instance as `target:` works — Turbo resolves `dom_id` on it automatically, no need to call `dom_id` yourself.
- `locals:` is not inferred beyond the caller's own default (`{ model_name.element.to_sym => self }`, e.g. `item: self`) — if the partial needs a different local name (e.g. broadcasting from `Item` but rendering `feeds/_feed`, which needs `feed:`), pass `locals:` explicitly.
- The `_later_to` variants (`broadcast_replace_later_to`, etc.) all funnel through `broadcast_action_later_to`, which enqueues `Turbo::Streams::ActionBroadcastJob` — that's the job class to assert against in tests (`assert_enqueued_with(job: Turbo::Streams::ActionBroadcastJob)`), not `Turbo::Streams::BroadcastJob` (that one's only used by `broadcast_render_later_to`, a different method).
- Use `_later_to` (not the synchronous form) when broadcasting from inside a controller action/request-response cycle — the gem's own docs say so explicitly, since synchronous broadcasting includes a render step that would otherwise block the response. Broadcasting from a model callback that already runs outside a request (e.g. `after_create_commit` triggered by a background job) is fine synchronously — that's the existing convention in `Item#broadcast_creation`.
- `Turbo::Broadcastable::TestHelper` (giving `assert_turbo_stream_broadcasts`/`assert_no_turbo_stream_broadcasts`/`capture_turbo_stream_broadcasts`) is mixed into `ActiveSupport::TestCase` by turbo-rails' engine, and it internally includes `ActionCable::TestHelper` too — but **not unconditionally at boot**. The mixin is nested inside `ActiveSupport.on_load(:action_cable) { ActiveSupport.on_load(:active_support_test_case) { include ... } }` (`turbo/engine.rb`), and `:action_cable` itself only fires as a side effect of `ActionCable::Server::Base` first loading (a top-level `ActiveSupport.run_load_hooks(:action_cable, Base.config)` at the bottom of actioncable's `server/base.rb`, executed whenever Zeitwerk autoloads that file — e.g. the first time some request in the process renders a view with `turbo_stream_from`). Left alone, this makes `assert_turbo_stream_broadcasts` genuinely undefined for any model test that happens to run before anything in the process has touched Action Cable — a real, seed-dependent Minitest flake (verified: reproduced with the default random seed, disappeared with a fixed one), not a hypothetical one. Fixed by forcing `ActionCable::Server::Base` to load unconditionally near the top of `test/test_helper.rb`, before `ActiveSupport::TestCase` is configured — don't remove that line under the assumption it's dead code. These assertions only observe *synchronous* broadcasts, regardless; for the `_later_to` async path, assert on the enqueued job instead. `ActiveJob::TestHelper` (`assert_enqueued_with`, `assert_no_enqueued_jobs`, etc.) is **not** auto-included anywhere by default — it's added explicitly in `test/test_helper.rb`.
- Turbo Frame navigation only extracts the *matching* `<turbo-frame>`'s inner content from a response and discards everything outside it (siblings included). Any `turbo_stream_from`/`turbo-cable-stream-source` tag meant to stay subscribed across a frame navigation must live *inside* the frame (or outside any frame entirely, for page-level subscriptions like the shared `:feeds` stream on `feeds/index.html.erb`) — a sibling tag simply never reaches the DOM when loaded via frame nav, even though it renders fine on a full page load.
- A full-page Turbo Drive visit (`PageRenderer` in `app/assets/javascripts/turbo.js`) never touches attributes on `<html>` except `lang`/`dir` (`#setLanguage()`, copied from the new snapshot on every visit). Anything else set on `<html>` — a `data-*` attribute, a class — is frozen from the very first page load and won't reflect a later response, even a redirect back to the same page. `<body>`, by contrast, is fully swapped every visit (`document.body.replaceWith(newElement)`), so any attribute that needs to change per-request (e.g. the signed-in user's `data-theme`, set in `app/views/layouts/application.html.erb` via `ApplicationHelper#theme_attribute`) belongs on `<body>`, not `<html>`.

**rss 0.3.3** (Ruby stdlib-adjacent `rss` gem): `RSS::Parser.parse` returns different object graphs for RSS (`RSS::Rss`, `.channel.items`, item `.pubDate`/`.guid.content`/`.description`) vs. Atom (`RSS::Atom::Feed`, `.entries`, entry `.published`/`.updated`/`.id.content`/`.summary.content`/`.content.content`, all text-construct fields wrapping the actual string behind `.content`). Atom's `<link>` can be multiple elements distinguished by `.rel` (`nil` means default `"alternate"`) — see `ParsedFeed`/`AtomLink` in the architecture section above. Full exact accessor list validated by parsing hand-built sample documents, not guessed.

**Rails 8.1.3's built-in authentication generator** (`bin/rails generate authentication`, source: `railties-8.1.3/lib/rails/generators/rails/authentication/`) — this is what `boring_rss` uses, not Devise or any other gem:
- It's a generator, not a library dependency — it writes real, editable files into `app/` that you own from that point on (no upgrade path via `bundle update`; changes to auth behavior are just normal code edits). Preview with `--pretend` before running for real; re-running without `--force`/`--skip` will prompt on every already-existing file.
- What it creates: `User`/`Session`/`Current` models (`Current < ActiveSupport::CurrentAttributes`, holding `.session`, delegating `.user`), `SessionsController` (login) + `PasswordsController` (reset) + views, an `Authentication` concern, `ApplicationCable::Connection`, a `PasswordsMailer`, and `CreateUsers`/`CreateSessions` migrations (generated, not auto-run). It also uncomments `gem "bcrypt"` in the Gemfile if already present (commented) and runs `bundle install`, or does `bundle add bcrypt` otherwise — a real environment mutation, not just file generation.
- **It ships zero self-registration UI.** Only login + password-reset. If you want a sign-up form, you build a `RegistrationsController` yourself, following the exact same conventions `SessionsController` uses (`allow_unauthenticated_access only: %i[new create]`, `start_new_session_for(user)`) — see `boring_rss`'s own `app/controllers/registrations_controller.rb` for a worked example. The generator assumes accounts are created via `rails console`/seeds otherwise.
- **`configure_application_controller` injects `include Authentication` directly into `ApplicationController`** — this means `before_action :require_authentication` applies to *every* controller/action in the app by default the moment the generator runs. Anything that should stay public (a login page, a sign-up page, a health check) needs an explicit `allow_unauthenticated_access` class-method call; there's no "public by default" mode.
- **`ApplicationCable::Connection#connect` calls `reject_unauthorized_connection` unless a valid signed `session_id` cookie resolves to a `Session`.** This means *every* Action Cable connection app-wide requires a logged-in user post-generation — including any existing Turbo Stream (`turbo_stream_from`) subscriptions. If an app has public, unauthenticated pages that rely on live broadcasts, this generator will silently break them (the cable connection gets rejected, not just the page) unless `ApplicationCable::Connection` is hand-edited to allow anonymous connections for those specific streams.
- The access pattern is `Current.user`/`Current.session` (a global `CurrentAttributes` singleton), not a `current_user` controller/view helper method — the generator doesn't define one. `authenticated?` (a `helper_method`) is the only boolean check provided out of the box.
- Test-side: `Turbo`-unrelated — the generator adds its own `test/test_helpers/session_test_helper.rb` defining `sign_in_as(user)`/`sign_out`, auto-included only into `ActionDispatch::IntegrationTest` (via `ActiveSupport.on_load(:action_dispatch_integration_test)`), **not** into plain `ActiveSupport::TestCase`. Every existing controller/integration test that hits a now-guarded action needs `sign_in_as(users(:one))` added to its `setup`; plain model tests are unaffected (no auth requirement at that layer) but need fixture associations updated (e.g. `feeds.yml` needs a `user:` reference once `Feed belongs_to :user`).
- `rate_limit to: 10, within: 3.minutes, only: :create` on `SessionsController#create` is Rails 8's built-in controller-level rate limiting (`ActionController::RateLimiting`), not a separate gem — worth knowing it exists as a pattern if other endpoints need throttling later.
